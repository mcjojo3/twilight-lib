# TwilightLib Mod - Comprehensive Developer Guide

## Overview
TwilightLib is a Minecraft Forge mod that provides player morphing, cosmetic addons (ears, tails, wings), particle trails, and special effects. The mod features a supporter tier system for unlocking exclusive cosmetics, with automatic synchronization across clients.

---

## Package Structure

### Core (mc.sayda.twilight_lib)

#### **TwilightLib.java**
**Package:** `mc.sayda.twilight_lib`

**Purpose:** Main mod entry point that initializes all systems and handles player lifecycle events.

**Key Responsibilities:**
- Registers capabilities (morph, addons, trails, effects) for player entities
- Initializes network channels, entities, particles, and configuration
- Handles player login, death/respawn, and capability persistence
- Auto-grants cosmetics based on supporter tier from GitHub JSON
- Synchronizes all player data (morphs, addons, trails, effects) across clients

**Important Methods:**
- `onRegisterCapabilities()` - Registers all four capability types
- `attachEntityCaps()` - Attaches capability providers to player entities
- `onPlayerLogin()` - Syncs player data on join, checks supporter status, auto-grants cosmetics
- `onPlayerClone()` - Restores capabilities after death using persistent NBT
- `onPlayerRespawn()` - Re-syncs all data after respawn

**Dependencies:** NetworkHandler, SupporterService, all capability providers, ModEntities, ModParticles, TwilightConfig

---

#### **TwilightConstants.java**
**Package:** `mc.sayda.twilight_lib`

**Purpose:** Centralized constants to prevent typos and simplify refactoring.

**Key Responsibilities:**
- Defines NBT tag names for persistent data storage
- Contains animation timing constants for addons

**Important Fields:**
- `NBT_MORPH`, `NBT_ADDONS`, `NBT_TRAILS`, `NBT_EFFECTS` - Persistent NBT keys
- `Animation.*` - Tail swing/wave animation parameters

**Dependencies:** None (pure constants)

---

#### **TwilightEventHandler.java**
**Package:** `mc.sayda.twilight_lib`

**Purpose:** Handles dynamic entity size and physics adjustments for morphed players.

**Key Responsibilities:**
- Adjusts player hitbox based on morphed entity dimensions
- Scales hitbox for different poses (swimming, crouching, fall flying)
- Dynamically adjusts step height based on morph size
- Updates eye height for proper camera positioning

**Important Methods:**
- `onEntitySize()` - Modifies player dimensions to match morphed entity
- `onPlayerTick()` - Updates step height every tick for seamless climbing

**Dependencies:** MorphProvider, TwilightConfig

### Capabilities (mc.sayda.twilight_lib.capabilities)

#### **IMorph.java / MorphData.java / MorphProvider.java**
**Package:** `mc.sayda.twilight_lib.capabilities`

**Purpose:** Manages player entity morphing (transforming into different mobs).

**Key Responsibilities:**
- Stores the ResourceLocation of the morphed entity type
- Caches the resolved EntityType for performance
- Serializes/deserializes morph state to NBT
- Provides capability access via `MorphProvider.MORPH_CAP`

**Important Methods/Fields:**
- `getEntityType()` - Returns Optional<ResourceLocation> of current morph
- `setEntityType()` - Changes morph and updates cached EntityType
- `getCachedEntityType()` - Returns EntityType<?> for quick dimension queries
- `serialize()/deserialize()` - NBT persistence

**Dependencies:** Minecraft's entity registry

---

#### **IAddons.java / AddonsData.java / AddonsProvider.java**
**Package:** `mc.sayda.twilight_lib.capabilities`

**Purpose:** Manages player cosmetic addons (ears, tails, wings, accessories).

**Key Responsibilities:**
- Tracks owned addons (what player has access to)
- Tracks active addons (what's currently equipped/visible)
- Supports multiple addons active simultaneously
- Serializes/deserializes addon state to NBT

**Important Methods/Fields:**
- `getAddons()` - Returns owned addons
- `addAddon()/removeAddon()` - Modify ownership
- `getActiveAddons()` - Returns currently equipped addons
- `setActiveAddon(id, active)` - Equip/unequip an addon
- `ADDONS_CAP` - Capability instance

**Dependencies:** None (pure data storage)

---

#### **ITrails.java / TrailsData.java / TrailsProvider.java**
**Package:** `mc.sayda.twilight_lib.capabilities`

**Purpose:** Manages player particle trails (cosmetic effects that follow movement).

**Key Responsibilities:**
- Tracks owned trails (what player has access to)
- Tracks active trail (only one can be active at a time)
- Supports enabling/disabling trails without changing selection
- Serializes/deserializes trail state to NBT

**Important Methods/Fields:**
- `getTrails()` - Returns owned trails
- `addTrail()/removeTrail()` - Modify ownership
- `getActiveTrail()` - Returns currently selected trail (or null)
- `setActiveTrail()` - Changes active trail
- `isTrailEnabled()/setTrailEnabled()` - Toggle rendering without losing selection
- `TRAILS_CAP` - Capability instance

**Dependencies:** None (pure data storage)

---

#### **IEffects.java / EffectsData.java / EffectsProvider.java**
**Package:** `mc.sayda.twilight_lib.capabilities`

**Purpose:** Manages player special effects (respawn effects, passive abilities).

**Key Responsibilities:**
- Tracks owned effects (what player has access to)
- Effects are always active when owned (no toggle)
- Serializes/deserializes effect state to NBT

**Important Methods/Fields:**
- `getEffects()` - Returns owned effects
- `addEffect()/removeEffect()` - Modify ownership
- `hasEffect()` - Check if player owns an effect
- `EFFECTS_CAP` - Capability instance

**Dependencies:** None (pure data storage)

### Commands (mc.sayda.twilight_lib.commands)

#### **TwilightLibCommands.java**
**Package:** `mc.sayda.twilight_lib.commands`

**Purpose:** Admin-level commands for morphing, trails, and effects (requires permission level 2).

**Key Responsibilities:**
- Morph/unmorph players into any LivingEntity
- Set/toggle trails for players
- Set/toggle effects for players
- List available options
- Validate entity types (caches valid living entities for performance)
- Support both command aliases (`/twilightlib` and `/tl`)

**Important Methods:**
- `registerCommands()` - Registers all command syntax
- `executeMorph()` - Validates and applies morph
- `executeSetTrail()` - Grants trail, activates it, and enables trails
- `executeToggleTrail()` - Toggles trail rendering
- `executeSetEffect()` - Grants effect to player
- `initializeEntityCache()` - Builds cache of valid morphable entities

**Dependencies:** MorphProvider, TrailsProvider, EffectsProvider, NetworkHandler, TrailType, CommandUtils

---

#### **AddonCommands.java**
**Package:** `mc.sayda.twilight_lib.commands`

**Purpose:** Admin commands for force-equipping/unequipping addons (requires permission level 2).

**Key Responsibilities:**
- Force-equip addons (bypasses ownership check)
- Force-unequip addons
- Clear all equipped addons
- List all registered addons
- Syncs changes across all clients

**Important Methods:**
- `registerCommands()` - Registers addon command syntax
- `executeEquipAddon()` - Force-activates addon without ownership check
- `executeUnequipAddon()` - Force-deactivates addon
- `executeClearAddons()` - Removes all equipped addons

**Dependencies:** AddonRegistry, AddonsProvider, NetworkHandler, CommandUtils

---

#### **CosmeticsCommand.java**
**Package:** `mc.sayda.twilight_lib.commands`

**Purpose:** Player-accessible commands for managing owned cosmetics (level 0, no permissions).

**Key Responsibilities:**
- Allow players to equip/unequip owned addons
- Allow players to set/toggle owned trails
- Display cosmetic ownership and tier information
- Show supporter tier benefits
- Prevent access to unowned cosmetics

**Important Methods:**
- `registerCommands()` - Registers `/cosmetics` command tree
- `equipAddon()/unequipAddon()` - Manages player's addon equipment
- `setTrail()/toggleTrail()` - Manages player's trail selection
- `listTrails()/listAddons()/listEffects()` - Shows owned cosmetics and tier unlocks
- `showInfo()` - Displays supporter status and cosmetic count

**Dependencies:** TrailsProvider, AddonsProvider, EffectsProvider, SupporterRegistry, SupporterService, NetworkHandler

---

#### **CommandUtils.java**
**Package:** `mc.sayda.twilight_lib.commands`

**Purpose:** Utility methods for command handling and feedback.

**Key Responsibilities:**
- Determine if command feedback should be sent to source
- Extract target player from command source

**Important Methods:**
- `shouldSendFeedbackToSource()` - Returns true if source is admin/console/different player
- `getTargetPlayer()` - Gets ServerPlayer from CommandSourceStack (or null)

### Network (mc.sayda.twilight_lib.network)

#### **NetworkHandler.java**
**Package:** `mc.sayda.twilight_lib.network`

**Purpose:** Central network channel manager for client-server synchronization.

**Key Responsibilities:**
- Initializes Forge SimpleChannel for mod packets
- Registers all packet types (morph, addons, trails, effects)
- Provides helper methods to broadcast data to all clients or specific players
- Syncs existing player data to newly joined players

**Important Methods:**
- `init()` - Registers all packet handlers
- `sendToAll()/sendToPlayer()` - Broadcasts packets
- `sendAllMorphsToPlayer()` - Syncs all existing morphs to new player
- `sendAllAddonsToPlayer()` - Syncs all active addons to new player
- `sendAllTrailsToPlayer()` - Syncs all trail data to new player
- `sendAllEffectsToPlayer()` - Syncs all effects to new player

**Dependencies:** All packet classes, all capability providers

---

#### **SyncMorphPacket.java**
**Package:** `mc.sayda.twilight_lib.network`

**Purpose:** Synchronizes player morph state from server to clients.

**Key Responsibilities:**
- Encodes/decodes player UUID and morph ResourceLocation
- Applies morph to client-side player capability
- Refreshes player dimensions after morph change
- Handles morph removal (Optional.empty())

**Important Methods:**
- `encode()` - Writes UUID and Optional<ResourceLocation> to buffer
- `decode()` - Reads packet data from buffer
- `handle()` - Applies morph on client side and refreshes dimensions

**Dependencies:** MorphProvider

---

#### **SyncAddonsPacket.java**
**Package:** `mc.sayda.twilight_lib.network`

**Purpose:** Synchronizes player active addons from server to clients.

**Key Responsibilities:**
- Encodes/decodes player UUID and active addon set
- Replaces client-side active addons with server state
- Clears old addons before applying new set

**Important Methods:**
- `encode()` - Writes UUID and Set<String> to buffer
- `decode()` - Reads packet data from buffer
- `handle()` - Applies active addons on client side

**Dependencies:** AddonsProvider

---

#### **SyncTrailsPacket.java**
**Package:** `mc.sayda.twilight_lib.network`

**Purpose:** Synchronizes player trail data from server to clients.

**Key Responsibilities:**
- Encodes/decodes player UUID and full trail data (CompoundTag)
- Deserializes trail data on client side
- Handles null NBT gracefully

**Important Methods:**
- `encode()` - Writes UUID and CompoundTag to buffer
- `decode()` - Reads packet data from buffer
- `handle()` - Deserializes trail data on client side

**Dependencies:** TrailsProvider

---

#### **SyncEffectsPacket.java**

**Purpose:** Synchronizes player effects from server to clients.

**Key Responsibilities:**

### Supporter System (mc.sayda.twilight_lib.supporter)

#### **SupporterService.java**
**Package:** `mc.sayda.twilight_lib.supporter`

**Purpose:** Fetches and caches supporter data from GitHub JSON endpoint.

**Key Responsibilities:**
- Asynchronously fetches supporter list on mod startup
- Caches data for 1 hour to reduce API calls
- Parses JSON to extract tier and manual cosmetic grants
- Provides thread-safe access to supporter data
- Prevents duplicate concurrent fetches

**Important Methods:**
- `fetchSupporters()` - Async fetch with caching
- `parseSupportersJson()` - Parses JSON into SupporterData objects
- `getSupporterData(uuid)` - Returns Optional<SupporterData> for player
- `isSupporter(uuid)` - Quick boolean check
- `forceRefresh()` - Clears cache and re-fetches

**Dependencies:** Gson for JSON parsing, SupporterData, SupporterRegistry

---

#### **SupporterData.java**
**Package:** `mc.sayda.twilight_lib.supporter`

**Purpose:** Data class representing a supporter's tier and cosmetic permissions.

**Key Responsibilities:**
- Stores supporter UUID, name, tier
- Stores manual cosmetic grants (persist even if tier expires)
- Combines tier unlocks with manual grants
- Determines if user is an active supporter

**Important Methods:**
- `isActiveSupporter()` - Returns true if tier is not null/"none"
- `getAllTrails()` - Merges tier unlocks + manual grants
- `getAllAddons()` - Merges tier unlocks + manual grants
- `getAllEffects()` - Merges tier unlocks + manual grants
- `getManualTrails()/Addons()/Effects()` - Returns only manual grants

**Dependencies:** SupporterRegistry for tier unlocks

---

#### **SupporterRegistry.java**
**Package:** `mc.sayda.twilight_lib.supporter`

**Purpose:** Defines which cosmetics are unlocked at each supporter tier.

**Key Responsibilities:**
- Hardcodes tier-based cosmetic unlocks (stone, bronze, silver, gold, platinum)
- Provides tier lookup methods
- Identifies supporter-exclusive cosmetics
- Separate from data fetching (static configuration)

**Important Methods:**
- `getTrailsForTier(tier)` - Returns trails for specific tier
- `getAddonsForTier(tier)` - Returns addons for specific tier
- `getEffectsForTier(tier)` - Returns effects for specific tier
- `isTrailSupporterExclusive()` - Checks if trail requires supporter status
- `getAllSupporterTrails()` - Returns all supporter-exclusive trails

**Dependencies:** None (static configuration)

---

## Data Flow

### Player Login Flow
1. Player connects → `TwilightLib.onPlayerLogin()`
2. Check supporter status via `SupporterService.getSupporterData(uuid)`
3. Auto-grant tier-based + manual cosmetics to capabilities
4. Save to persistent NBT
5. Sync all morphs/addons/trails/effects from existing players to new player
6. Sync new player's data to all existing players

### Morph Application Flow
1. Admin runs `/tl morph minecraft:fox Player123`
2. `TwilightLibCommands.executeMorph()` validates entity type
3. `setMorph()` updates capability and persistent NBT
4. `NetworkHandler.sendToAll()` broadcasts SyncMorphPacket
5. Clients receive packet → `SyncMorphPacket.handle()` updates capability
6. `TwilightEventHandler.onEntitySize()` adjusts hitbox
7. `MorphRenderHandler.onRenderPlayerPre()` replaces player render with entity

### Addon Rendering Flow
1. Player equips addon via `/cosmetics addons equip kitsune_ears_white`
2. Capability updated, synced via SyncAddonsPacket
3. Client receives addon list in capability
4. `PlayerAddonLayer.render()` iterates active addons
5. For each addon: get/bake model, sync parts with player, call setupAnim(), render

### Trail Rendering Flow
1. `TrailRenderer.onClientTick()` runs every tick
2. Check if trail enabled, player moving, update frequency
3. Look up `TrailType.fromId(activeTrail)`
4. If tier-based (hearts), look up supporter tier from `SupporterService`
5. Spawn particles at player's feet with randomized offsets

## Architecture Patterns

### Capability Pattern
All player data uses Forge capabilities for:
- Automatic attachment to player entities
- Serialization/deserialization to NBT
- Network synchronization
- Clean separation of concerns

### Registry Pattern
Addons use a central registry for:
- Thread-safe concurrent mod loading
- Lookup by ID for commands
- Enumeration for listings
- Decoupled registration from usage

### Packet Pattern
All client-server sync uses dedicated packet classes:
- Type-safe encoding/decoding
- Clear data contracts
- Single responsibility per packet
- Consistent handling pattern

### LRU Cache Pattern
Addon models use LRU caching for:
- Performance (avoid rebaking)
- Memory management (evict old models)
- Configurable size limits
- Access-ordered eviction

## Extension Points

### Adding New Addons
1. Create model class extending `BaseAddonModel`
2. Override body part getters (head, body, arms, legs)
3. Optionally override `setupAnim()` for custom animations
4. Register in `AddonInit.registerAddons()` with ID, layer, texture
5. Add to supporter tier in `SupporterRegistry` if exclusive

### Adding New Trail Types
1. Add enum value to `TrailType` with particle and count
2. Add to supporter tier in `SupporterRegistry` if exclusive
3. Trail automatically works with existing rendering system

### Adding New Effects
1. Add effect ID string to `SupporterRegistry` tier
2. Create handler class subscribing to relevant events
3. Check for effect in `EffectsProvider` capability
4. Implement effect logic (particles, sounds, gameplay changes)

### Adding New Commands
1. Create command class with `registerCommands()` method
2. Use `CommandUtils` for target player resolution
3. Register in `TwilightLib` event bus listener
4. Use `NetworkHandler` to sync changes to clients

## Performance Considerations

### Addon Model Caching
- LRU cache prevents memory bloat from hundreds of models
- Default 150 models cached (configurable 10-500)
- Access-ordered eviction removes unused models first
- No manual cleanup needed (GC handles evicted models)

### Trail Rendering
- Update frequency configurable (default 3 ticks)
- Movement check prevents spawning when standing still
- Horizontal velocity only (ignores jumping/falling)
- Per-player capability check (no global iteration)

### Entity Morph Caching
- Single proxy entity per player (reused across frames)
- Cached EntityType for dimension queries
- Entity registry cache for command suggestions
- Cache invalidation on registry changes

### Network Optimization
- Only sync changes, not full state every tick
- Packet batching for multiple players
- CompoundTag for complex data (trails)
- Primitive sets for simple lists (addons, effects)

## Supporter System

### JSON Format (GitHub)
```json
{
  "supporters": [
    {
      "uuid": "player-uuid-here",
      "name": "PlayerName",
      "tier": "gold",
      "cosmetics": {
        "trails": ["special_trail"],
        "addons": ["exclusive_addon"],
        "effects": ["rare_effect"]
      }
    }
  ]
}
```

### Tier Hierarchy
- **Stone**: Entry tier (no cosmetics yet)
- **Bronze**: Basic trails (hearts)
- **Silver**: More trails (hearts, sparkles, cherry_blossom), galaxy_tail addon
- **Gold**: All trails + exclusive effects (respawn_twilight)
- **Platinum**: All benefits (future-proof tier)

### Manual Grants
- Stored in `cosmetics` field of JSON
- Persist even if tier expires or changes
- Used for gifts, event rewards, grandfathered perks
- Combined with tier unlocks in `SupporterData.getAllTrails/Addons/Effects()`

## Common Debugging Tips

### Player not morphing?
- Check capability attached: Log in `attachEntityCaps()`
- Check packet received: Log in `SyncMorphPacket.handle()`
- Check entity type valid: Look for validation errors in morph command
- Check cache: Entity might not be LivingEntity

### Addons not rendering?
- Check addon registered: `/tl addon list`
- Check player has addon: Check capability data
- Check model baked: Log in `getOrBakeModel()`
- Check texture path: Ensure texture exists in assets

### Trails not showing?
- Check trail enabled: `ITrails.isTrailEnabled()`
- Check player moving: Horizontal velocity > 0.01
- Check update frequency: Config might be too high
- Check particle registered: Verify in ModParticles

### Supporter data not loading?
- Check network connection: GitHub fetch might fail
- Check JSON format: Parse errors logged
- Check UUID matches: Use player's UUID string
- Force refresh: Restart server or use debug command

## Known Limitations

### Morphing
- Only works with LivingEntity types
- Player entity type (minecraft:player) not allowed
- Some entities may have rendering issues (e.g., ender dragon)
- Hitbox changes might cause clipping through blocks

### Addons
- Limited to 6 body parts (head, body, arms, legs)
- No dynamic model part creation
- Texture must be predefined (no runtime generation)
- Cache eviction might cause brief lag when rebaking

### Trails
- No particle collision detection
- Particle count fixed per trail type
- No per-player particle limits (could lag with many players)
- Tier-based trails require supporter service fetch

### Supporter System
- Requires GitHub access (fails if offline/blocked)
- 1-hour cache delay before new supporters appear
- Manual grants can't be modified in-game (requires JSON edit + restart)
- No in-game tier management
